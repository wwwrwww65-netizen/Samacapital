# وثيقة متطلبات وتصميم وتنفيذ الموقع الإلكتروني لشركة سما كابيتال

> **اسم المشروع:** SAMA CAPITAL — سما كابيتال  
> **نوع المشروع:** موقع شركة احترافي لخدمات الاستيراد والشحن والتخليص الجمركي، مع لوحة إدارة ونظام استقبال طلبات عروض الأسعار والاستفسارات.  
> **اللغات الأساسية:** العربية والإنجليزية.  
> **الأولوية:** تجربة مستخدم ممتازة، تصميم بصري حديث، سرعة عالية، وضوح الخدمات، سهولة التواصل وإرسال طلب الشحن، وتجربة متكاملة على الجوال والكمبيوتر والأجهزة اللوحية.

## 0. تعليمات أساسية للمطور — اقرأ قبل البدء

هذه الوثيقة هي مرجع المشروع الأساسي. المطلوب **إنشاء موقع متكامل قابل للاستخدام الفعلي والإدارة والنشر**، وليس صفحة تعريفية واحدة أو نموذج تصميم ثابت.

1. اقرأ الوثيقة كاملة، ثم ضع خطة تنفيذ ومراحل واضحة قبل كتابة الكود.
2. افحص الشعار والصور المرفقة واستعملها مرجعًا للهوية، مع تحسين جودة الأصول بصريًا وعدم تشويه الشعار.
3. لا تستخدم نصوصًا تجريبية أو أرقامًا وهمية أو إحصاءات أو تقييمات أو شعارات عملاء أو شهادات اعتماد غير موثقة.
4. لا تخترع أسعار شحن أو مدد وصول أو جداول رحلات أو تغطية جغرافية أو وعودًا جمركية. أي معلومة تشغيلية يجب أن تعتمدها إدارة الشركة.
5. لا تُظهر ميزة تتبع شحنات حقيقية ما لم يوجد مصدر بيانات أو تكامل فعلي يزوّد الموقع بحالة الشحنة. لا تنشئ حالات تتبع وهمية بغرض إظهار أن الصفحة تعمل.
6. يجب أن تعمل جميع الروابط والأزرار والنماذج والتنقلات. يمنع وضع زر شكلي لا يؤدي وظيفة واضحة.
7. أنشئ العربية من اليمين إلى اليسار RTL والإنجليزية من اليسار إلى اليمين LTR بصورة صحيحة في كامل الموقع، وليس بمجرد محاذاة النص.
8. اجعل المحتوى والصور والأرقام والخدمات والعناوين وبيانات التواصل قابلة للتعديل من لوحة الإدارة، ما عدا العناصر التقنية التي لا ينبغي أن تكون قابلة للتعديل للمستخدم العادي.
9. افصل بيانات الشركة عن الكود. لا تكرر أرقام الهاتف أو العنوان أو أسماء الخدمات في ملفات كثيرة؛ استخدم إعدادات مركزية وقاعدة بيانات أو نظام محتوى واضحًا.
10. اعتمد مبدأ Mobile First، ثم وسّع التصميم للشاشات الأكبر. لا تصمم نسخة كمبيوتر ثم تصغّرها للجوال.
11. نفّذ حالات التحميل والنجاح والفشل وعدم وجود بيانات والاتصال الضعيف. يجب ألا يرى المستخدم صفحة بيضاء أو واجهة مكسورة.
12. سلّم المشروع مع الكود المصدري، قاعدة البيانات وترحيلاتها، ملف متغيرات البيئة النموذجي، تعليمات التثبيت والتشغيل والنشر والنسخ الاحتياطي، ونتائج الاختبارات.
13. لا تكتفِ بإنهاء الواجهة. يجب إكمال العمل من أول زيارة للموقع إلى إرسال الطلب واستلامه وإدارته من لوحة التحكم.
14. قبل الإطلاق، اعرض نسخة تجريبية على الشركة لمراجعة النصوص والخدمات والأرقام والعنوان والصور واللغة الإنجليزية، ولا تنشر أي معلومة غير معتمدة.

## 1. فهم الشركة والهوية من المواد المرفقة

### 1.1 الاسم والكتابة المعتمدة

- الاسم العربي: **سما كابيتال**.
- الاسم الإنجليزي: **SAMA CAPITAL**.
- يستخدم الشعار الرسمي المرفق دون إعادة رسمه بطريقة تغيّر رموزه أو نسبه.
- النشاط كما يظهر في المواد: **الاستيراد وخدمات الشحن والتخليص الجمركي**.
- الرسائل التسويقية الظاهرة في التصاميم تشير إلى مساعدة العملاء في إجراءات الشحن والتخليص، وإتاحة حلول للنقل إلى أنحاء اليمن.
- يظهر في الشعار رمز طائرة وسفينة، ولذلك يمكن تقديم مفهوم النقل الجوي والبحري بصريًا، لكن يجب التأكد من أن الشركة توفر كلا النوعين فعليًا قبل نشر صفحات خدمات مستقلة لهما.

### 1.3 اتجاه العلامة التجارية

الهوية المطلوبة مؤسسية وموثوقة وحديثة، وتجمع بين:

- **الثقة والاحتراف:** واجهة شركة لوجستية تتعامل مع بضائع ووثائق وإجراءات تجارية.
- **الوضوح والسهولة:** شرح الخدمة وخطواتها بلغة بسيطة، وإبراز طريقة التواصل وطلب التسعير.
- **الانتشار والحركة:** إيحاءات مدروسة بالموانئ والطائرات والحاويات والطرق وسلاسل الإمداد.
- **الطابع المحلي والدولي:** حضور واضح لليمن مع فهم أن الاستيراد والشحن يرتبطان بجهات وأسواق خارجية.

- للإنجليزية والأرقام: استخدم الخط المتوافق بصريًا مع الخط العربي، مع اختبار شكل الأرقام وعلامات الترقيم.

## 2. أهداف الموقع ومقاييس نجاحه

### 2.1 الأهداف التجارية

1. تعريف الزائر بالشركة وخدماتها بوضوح خلال ثوانٍ.
2. تحويل الزوار إلى استفسارات وطلبات عروض أسعار مؤهلة.
3. تسهيل التواصل مع المكتب أو ممثل الشركة في اليمن والصين.
4. شرح مراحل العمل وتقليل مخاوف العميل من إجراءات الاستيراد والشحن والتخليص.
5. دعم العملاء الحاليين من خلال التتبع أو الاستفسار عن الشحنات عند توفر تكامل حقيقي.
6. بناء حضور رقمي ثنائي اللغة يمكن تهيئته لمحركات البحث.
7. تمكين فريق الشركة من تحديث المحتوى ومتابعة الطلبات دون الرجوع للمطور في كل تعديل.

### 2.2 مؤشرات القياس

تُضاف أدوات القياس بعد اعتماد سياسة الخصوصية، ويُقاس على الأقل:

- زيارات الصفحات ومصادر الوصول.
- الضغط على أرقام الاتصال وواتساب والبريد.
- بدء نموذج طلب التسعير، وإكماله، ومعدل تركه.
- عدد الطلبات المرسلة، ومعدل الطلبات الصحيحة مقابل المزعجة.
- أكثر الخدمات والصفحات التي تجذب طلبات.
- أخطاء النماذج والأجهزة أو المتصفحات التي تظهر فيها.
- مؤشرات الأداء الأساسية للويب Core Web Vitals.

لا تخزن بيانات حساسة أكثر مما يلزم، ولا ترسل محتوى النماذج أو المستندات إلى أدوات التحليلات.

## 3. التقنيات والبنية المقترحة

### 3.1 الاختيار التقني الأساسي

استخدم تقنيات حديثة مستقرة ومدعومة وقت التنفيذ. التوصية الحالية للمشروع:

| الطبقة | الاختيار المقترح | السبب |
|---|---|---|
| إطار الموقع | Next.js 16.x باستخدام App Router | صفحات سريعة، عرض من الخادم، توجيه، وتهيئة SEO جيدة |
| واجهة التفاعل | React 19.3 أو أحدث إصدار مستقر متوافق | بناء مكونات تفاعلية حديثة |
| اللغة | TypeScript مع `strict: true` | تقليل أخطاء الأنواع وتحسين قابلية الصيانة |
| التنسيق | Tailwind CSS 4.3.x أو أحدث إصدار مستقر | نظام تصميم متناسق وسريع التطوير |
| مكونات الوصول | مكونات مبنية على Radix UI أو بديل ملتزم بإمكانية الوصول، مع تخصيص بصري | قوائم ونوافذ ونماذج قابلة للاستخدام بلوحة المفاتيح |
| التحقق من البيانات | Zod أو مكتبة متوافقة | التحقق من المدخلات في الخادم والواجهة |
| قاعدة البيانات | PostgreSQL بإصدار مستقر مدعوم | بيانات الطلبات والمحتوى والمستخدمين |
| ORM | Prisma أو بديل ناضج متوافق مع PostgreSQL | مخطط واضح وترحيلات قاعدة البيانات |
| النماذج | React Hook Form مع Zod عند الحاجة | نماذج متعددة الخطوات دون تعقيد زائد |
| الاختبارات | Vitest + Playwright + axe أو أدوات مكافئة | اختبارات منطقية وتجربة متصفح وإمكانية وصول |
| إدارة الحزم | pnpm أو npm مع ملف lock ملتزم بالمستودع | تثبيت قابل للتكرار |
| النشر | Docker أو نشر Node.js مدعوم على خادم موثوق | بيئة متسقة وقابلة للتحديث |

**ملاحظة الإصدارات:** لا تثبّت نسخة قديمة لمجرد أنها وردت هنا. عند بدء التنفيذ افحص أحدث إصدار مستقر ومدعوم من كل تقنية، وتأكد من توافقها مع بعضها، ثم ثبّت إصدارات محددة في ملفات المشروع واحفظ ملف lock. يمنع الاعتماد على إصدارات Canary أو تجريبية في الإنتاج ما لم توجد موافقة تقنية مكتوبة.

### 3.2 المعمارية

ابدأ بتطبيق واحد منظم (Modular Monolith) بدل تقسيم المشروع إلى خدمات مصغّرة لا يحتاجها هذا النطاق. افصل بوضوح بين:

- واجهة الزوار العامة.
- واجهات النماذج والتفاعلات.
- وظائف الخادم وقواعد التحقق.
- قاعدة البيانات.
- لوحة الإدارة.
- مزودي الخدمات الخارجية: البريد، واتساب، تخزين الملفات، التحليلات، والتتبع.

استخدم Server Components افتراضيًا، ولا تجعل الصفحة Client Component كاملة دون ضرورة. استخدم المكونات العميلة فقط لما يحتاج تفاعلًا فعليًا مثل القوائم والنماذج والتبويبات.

### 3.3 ضوابط تقنية

- فعّل TypeScript strict، وفحص ESLint، والتنسيق الآلي للكود.
- لا تضع مفاتيح API أو كلمات المرور أو أسرار الخدمات في ملفات الواجهة أو المستودع.
- أضف `.env.example` بمتغيرات وهمية موضحة، دون أسرار فعلية.
- افصل إعدادات التطوير والاختبار والإنتاج.
- استخدم ترحيلات قاعدة بيانات versioned migrations؛ لا تعتمد على تعديل يدوي غير موثق في الإنتاج.
- لا تستخدم `localStorage` لتخزين أسرار الجلسات أو بيانات الطلبات الحساسة.
- لا تسمح باستدعاء قاعدة البيانات مباشرة من المتصفح.
- حافظ على سجلات أخطاء مفيدة دون تسجيل كلمات المرور أو رموز الجلسات أو محتوى المستندات.

## 5. تجربة المستخدم الرئيسية — من أول زيارة إلى إنجاز الهدف

### 5.1 المسارات الأساسية للزائر

**المسار الأول: زائر يريد معرفة الخدمات**

الرئيسية ← الخدمات ← صفحة خدمة ← كيف نعمل ← طلب عرض سعر أو اتصال.

**المسار الثاني: زائر مستعد لطلب شحن**

الرئيسية أو أي صفحة خدمة ← طلب عرض سعر ← إدخال بيانات الشحنة ← مراجعة البيانات ← إرسال ← رسالة تأكيد ورقم مرجعي.

**المسار الثالث: عميل يريد معرفة حالة شحنة**

الرئيسية ← تتبع الشحنة ← إدخال رقم التتبع ← عرض حالة حقيقية من مصدر موثوق. إذا لم يتوفر الربط، اعرض بوضوح طريقة الاستفسار اليدوي بدل إظهار نتيجة مصطنعة.

**المسار الرابع: زائر يريد التواصل مباشرة**

زر الاتصال أو واتساب أو صفحة التواصل ← اختيار قناة التواصل المناسبة ← فتح تطبيق أو إجراء اتصال بالرقم الصحيح.

### 5.2 مبادئ الاستخدام

- اجعل الهدف الأساسي لكل شاشة واضحًا.
- لا تضع أكثر من دعوة رئيسية واحدة بارزة في المنطقة نفسها.
- اجعل زر طلب عرض السعر ظاهرًا في الرأس وفي نهاية الصفحات المهمة.
- استخدم تسميات مباشرة مثل «اطلب عرض سعر» و«تواصل معنا» و«تتبّع شحنتك».
- لا تستخدم عبارات مبهمة مثل «ابدأ الآن» إن لم توضّح ماذا سيحدث بعد الضغط.
- حافظ على موضع التنقل متسقًا.
- لا تفتح نوافذ منبثقة تلقائيًا عند تحميل الصفحة.
- اجعل النماذج قصيرة قدر الإمكان، مع تقسيم الحقول المعقدة إلى خطوات واضحة.
- اعرض سبب طلب كل معلومة عند الحاجة، ولا تطلب معلومات لا تحتاجها الشركة.
- بعد إرسال الطلب، اشرح الخطوة التالية المتوقعة دون وعد بزمن رد غير معتمد.

## 6. تفاصيل التصميم والصفحات

### 6.1 الهيكل العام لكل الصفحات

**الشريط العلوي (Top Bar):**
- رقم الاتصال في اليمن ورقم الصين بعد تأكيدهما.
- اختصار واتساب إذا كان الرقم يدعمه فعلًا.
- اختيار اللغة العربية / English.
- أوقات التواصل عند اعتمادها.
- يجب أن يكون مختصرًا ولا يستهلك مساحة كبيرة على الهاتف.

**رأس الموقع (Header):**
- الشعار في موضع واضح مع رابط للرئيسية.
- قائمة الصفحات الأساسية.
- زر «اطلب عرض سعر» بارز.
- قائمة جوال قابلة للاستخدام باللمس ولوحة المفاتيح.
- عند التمرير يمكن استخدام رأس ثابت صغير، بشرط ألا يغطي المحتوى أو يسبب قفزة في التخطيط.

**منطقة المحتوى:**
- عنوان واضح لكل صفحة.
- مسار تنقل Breadcrumb في الصفحات الداخلية.
- مساحة قراءة مناسبة وعرض محتوى منضبط.

**التذييل (Footer):**
- الشعار وتعريف موجز معتمد.
- روابط الصفحات والخدمات.
- أرقام الاتصال والعنوان.
- روابط الشبكات الاجتماعية عند تزويد الشركة بها.
- روابط الخصوصية والشروط.
- حقوق النشر واسم الشركة.
- لا تضع أيقونات اجتماعية لا ترتبط بحسابات حقيقية.

### 6.2 الصفحة الرئيسية

ترتيب الأقسام المقترح:

1. **Hero Section**
   - عنوان عربي قوي مستوحى من الرسالة الإعلانية: «شحنك واستيرادك… بإجراءات أوضح وخطوات أسهل» أو صياغة تعتمدها الشركة.
   - نص فرعي قصير يشرح أن الشركة تقدم خدمات الاستيراد والشحن والتخليص الجمركي وفق الخدمات المعتمدة.
   - زر أساسي «اطلب عرض سعر».
   - زر ثانوي «تواصل مع فريقنا».
   - صورة رئيسية احترافية ذات صلة حقيقية بالشحن البحري أو الجوي أو الحاويات، دون تشويش خلف النص.
   - تجنب كتابة نصوص مهمة داخل الصورة نفسها؛ يجب أن تبقى النصوص قابلة للقراءة والفهرسة والتعديل.

2. **شريط الثقة والمعلومات**
   - يمكن عرض مواقع المكتب أو الأسواق أو أنواع الخدمات فقط إذا تم اعتمادها.
   - لا تعرض أرقامًا مثل «آلاف الشحنات» أو «سنوات خبرة» دون مستند أو موافقة.

3. **قسم الخدمات**
   - بطاقات واضحة لكل خدمة مؤكدة.
   - لكل بطاقة عنوان، شرح من سطرين، صورة أو أيقونة، ورابط للتفاصيل.
   - لا تعرض خدمة غير متاحة فعليًا.

4. **قسم لماذا سما كابيتال؟**
   - نقاط قيمة حقيقية تعتمدها الإدارة، مثل تسهيل الإجراءات أو متابعة الطلب أو تنسيق الشحن، إذا كانت صحيحة.
   - تجنب ادعاءات «الأسرع» و«الأرخص» و«الأفضل» دون دليل.

5. **قسم كيف نعمل؟**
   - استفسار العميل.
   - استلام تفاصيل البضاعة والوجهة.
   - مراجعة الاحتياج وتقديم العرض.
   - تنفيذ إجراءات الشحن والخدمات المتفق عليها.
   - متابعة الشحنة والتسليم وفق نطاق مسؤولية الشركة.
   - عدّل الخطوات وفق الإجراء الفعلي المعتمد؛ لا توحِ بأن كل المراحل تقع تحت سيطرة الشركة إذا كان بعضها لدى جهات خارجية.

6. **قسم نطاق الخدمة / الوجهات**
   - خريطة أو قائمة مناطق فقط بعد اعتمادها.
   - لا تضع مسارات مباشرة أو خطوطًا بين دول كأنها رحلات مؤكدة دون بيانات.

7. **قسم دعوة لاتخاذ إجراء**
   - رسالة قصيرة مع زر لطلب عرض السعر.

8. **الأسئلة الشائعة المختارة**
   - من 4 إلى 6 أسئلة رئيسية، مع رابط إلى صفحة الأسئلة الشائعة.

9. **قسم التواصل المختصر**
   - الهاتف، واتساب إن كان متاحًا، الموقع، ونموذج مختصر اختياري.

### 6.3 صفحة من نحن

تتضمن:
- تعريفًا رسميًا بالشركة يكتبه أو يعتمده المسؤول.
- مجال العمل بوضوح.
- الرؤية والرسالة والقيم إذا كانت للشركة صياغة رسمية.
- أسلوب خدمة العملاء والتعامل مع طلبات الاستيراد والشحن.
- صور حقيقية للمكتب أو الفريق أو العمليات بعد موافقة الشركة.
- لا تنشئ تاريخ تأسيس أو قصة إنجاز أو شهادات اعتماد من عندك.

### 6.4 صفحة الخدمات

اعرض الخدمات على هيئة بطاقات مرتبة، وتكون قابلة للإدارة. تصنيفات أولية للنقاش مع الشركة، وليست إعلانًا تلقائيًا عن توفر كل خدمة:

- خدمات الاستيراد.
- الشحن البحري.
- الشحن الجوي.
- التخليص الجمركي.
- تنسيق النقل والتوصيل داخل اليمن.
- خدمات الأعمال والشحنات التجارية.

**شرط النشر:** يجب أن تؤكد الشركة لكل خدمة: هل تقدمها مباشرة أم عبر شركاء؟ ما نطاقها؟ ما أنواع البضائع المقبولة؟ ما الاستثناءات؟ ما المستندات المطلوبة؟ وما مسؤولية الشركة وحدود الخدمة؟ احذف أو أخفِ أي خدمة لم يتم اعتمادها.

### 6.5 صفحة تفاصيل الخدمة

يحتوي قالب كل خدمة على:
- عنوان الخدمة.
- ملخص يشرح ما الذي يحصل عليه العميل.
- لمن تناسب الخدمة.
- ما البيانات التي يحتاج العميل إلى تجهيزها.
- آلية العمل خطوة بخطوة.
- حدود الخدمة والاستثناءات عند الحاجة.
- الأسئلة المرتبطة بها.
- دعوة لطلب عرض سعر مع تعبئة نوع الخدمة مسبقًا في النموذج.
- روابط لخدمات مرتبطة.

### 6.6 صفحة كيف نعمل

صممها كرحلة مرئية بسيطة، بأرقام أو خطوات متتابعة:

1. يرسل العميل تفاصيل الطلب.
2. يراجع الفريق نوع البضاعة ومسار الشحن والاحتياج.
3. يتواصل الفريق لتوضيح التفاصيل وتقديم عرض معتمد.
4. يتم الاتفاق على الخدمة والمستندات والشروط.
5. تُتابع العملية وفق المعلومات المتاحة والمسؤوليات المتفق عليها.

أظهر أن الأسعار والمدد النهائية تعتمد على تفاصيل الشحنة والمسار والجهات ذات العلاقة إذا كان ذلك مطابقًا لسياسة الشركة.

### 6.7 صفحة القطاعات

يمكن تفعيلها عند اعتماد الفئات التي تخدمها الشركة، مثل:
- التجار والمستوردين.
- الشركات والمؤسسات.
- المتاجر والمشروعات التجارية.
- الأفراد.

لا تنشر وعودًا مختلفة أو أسعارًا خاصة لكل فئة إلا إذا كانت معتمدة.

### 6.8 صفحة الوجهات والتغطية

- قائمة قابلة للبحث أو بطاقات للدول والمدن.
- إظهار الوجهة ونوع الخدمة المتاح بها فقط.
- توضيح أن التغطية قد تختلف باختلاف نوع الشحنة والخدمة إذا كان ذلك صحيحًا.
- لا تعرض خريطة مليئة بنقاط غير حقيقية.

### 6.9 صفحة طلب عرض سعر

هذه أهم صفحة تحويل في الموقع. يجب أن يكون النموذج مريحًا وسهلًا خصوصًا على الجوال.

**مقدمة النموذج:**
- عنوان مباشر.
- توضيح أن إرسال الطلب لا يعني قبول الشحنة أو تثبيت السعر.
- تقدير مبسط لما يحتاج العميل تجهيزه.

**النموذج متعدد الخطوات المقترح:**

**الخطوة الأولى — نوع الطلب**
- نوع الخدمة المطلوبة: قائمة ديناميكية بالخدمات المعتمدة.
- نوع العميل: فرد / شركة / تاجر / أخرى، إذا كان هذا التصنيف مفيدًا للشركة.
- هل الطلب استيراد جديد أم شحنة قيد الترتيب أم استفسار؟ بحسب سير العمل.

**الخطوة الثانية — معلومات الشحنة**
- وصف البضاعة.
- فئة البضاعة من قائمة قابلة للإدارة، مع خيار «أخرى».
- بلد أو مدينة الإرسال.
- بلد أو مدينة الوصول.
- نوع النقل المطلوب إذا كان متاحًا: بحري / جوي / بري / غير متأكد.
- الوزن التقريبي إن كان معروفًا.
- الحجم أو الأبعاد إن كانت معروفة.
- عدد القطع أو الطرود أو الحاويات إن كان مناسبًا.
- تاريخ الجاهزية أو التاريخ المتوقع، اختياري.
- هل يحتاج العميل إلى تخليص جمركي أو خدمات إضافية؟ خيارات معتمدة.
- ملاحظات إضافية.

**الخطوة الثالثة — بيانات التواصل**
- الاسم الكامل.
- اسم الشركة، اختياري.
- رقم الهاتف مع مفتاح الدولة، مع اقتراح `+967` افتراضيًا دون إجبار كل العملاء على اليمن.
- البريد الإلكتروني، اختياري ما لم تعتمد الشركة جعله مطلوبًا.
- وسيلة التواصل المفضلة: اتصال / واتساب / بريد.
- اللغة المفضلة للتواصل عند الحاجة.

**الخطوة الرابعة — المرفقات والمراجعة**
- إرفاق صور أو مستندات عند الحاجة فقط.
- ملخص واضح للبيانات المدخلة.
- إمكانية الرجوع لتعديل الخطوات السابقة دون فقدان البيانات.
- موافقة صريحة على سياسة الخصوصية.
- زر الإرسال النهائي.

**قواعد النموذج:**
- الحقول المطلوبة محددة بعلامة واضحة.
- التحقق من البيانات في المتصفح والخادم معًا.
- رسائل الخطأ بجوار الحقل باللغة المختارة.
- لا تمسح جميع المدخلات إذا حدث خطأ.
- امنع النقر المتكرر أثناء الإرسال.
- اعرض مؤشر تقدم واضح.
- اعرض صفحة نجاح تحتوي على رقم طلب مرجعي غير متسلسل بصورة تكشف أعداد الطلبات، وتوضح أن الفريق سيراجع الطلب ويتواصل وفق آلية الشركة.
- أرسل إشعارًا إلى فريق الشركة عبر البريد أو النظام الداخلي بعد إعداد المزود.
- أرسل تأكيدًا للعميل فقط عبر القنوات التي تم إعدادها وموافقة الشركة عليها.
- إن فشل إرسال الإشعار، احفظ الطلب بصورة آمنة وسجّل الخطأ، ولا تعرض للعميل نجاحًا كاذبًا إذا لم يتم حفظ الطلب.

### 6.10 صفحة تتبع الشحنة

**هذه الميزة مشروطة بتوفر نظام تتبع حقيقي.**

إذا كانت لدى الشركة واجهة API أو قاعدة تشغيلية موثوقة:
- حقل رقم التتبع.
- تحقق من تنسيق الرقم دون كشف ما إذا كانت أرقام شحنات العملاء الآخرين موجودة.
- حالة واضحة ومحدّثة من المصدر.
- خط زمني للأحداث مع التاريخ والوقت والمنطقة الزمنية عند توفرها.
- آخر تحديث ومصدره.
- الموعد المتوقع للتسليم فقط إذا أرسله المصدر.
- تفسير مبسط للحالات.
- زر التواصل بشأن الشحنة.
- حماية من كثرة محاولات الاستعلام.

إذا لم يتوفر تكامل:
- لا تعرض زر تتبع يؤدي إلى بيانات وهمية.
- يمكن إخفاء صفحة التتبع من القائمة، أو جعلها صفحة «استفسر عن شحنتك» بنموذج يطلب رقم الشحنة ووسيلة التواصل ويرسل الاستفسار للفريق.
- وضّح للعميل أن الاستعلام سيُراجع من فريق الشركة، ولا تعرض حالة مباشرة غير موجودة.

### 6.11 الأسئلة الشائعة

- تصنيفات للأسئلة: الشحن، الاستيراد، التخليص، المستندات، الأسعار، المتابعة.
- بحث بسيط أو مرشحات عند كثرة الأسئلة.
- أقسام قابلة للفتح والإغلاق مع توافق لوحة المفاتيح.
- إجابات معتمدة من الشركة فقط.
- زر متعلق بالسؤال لطلب عرض سعر أو التواصل.
- لا تقدم استشارات قانونية أو جمركية حاسمة دون اعتماد مختص من الشركة.

### 6.12 المقالات والأخبار

- صفحة قائمة بمقالات مع تصنيف وبحث عند الحاجة.
- صفحة مقال تحتوي على عنوان ووصف وصورة رئيسية واسم محرر وتاريخ نشر وتحديث ومحتوى منسق.
- جدول محتويات تلقائي للمقالات الطويلة.
- روابط مقالات ذات صلة.
- بيانات SEO ومشاركة اجتماعية.
- لا تنشر أخبارًا أو معلومات جمركية قديمة على أنها حديثة.
- يجب إظهار تاريخ آخر تحديث للمحتوى الإجرائي.

### 6.13 صفحة تواصل معنا

- أرقام اليمن والصين بعد التحقق، بروابط `tel:`.
- رابط واتساب صحيح عند تأكيد استخدام واتساب، مع رسالة افتتاحية واضحة.
- العنوان المعتمد ورابط خرائط دقيق عند توفيره.
- ساعات العمل والمنطقة الزمنية بعد اعتمادها.
- نموذج تواصل مختصر: الاسم، الهاتف أو البريد، الموضوع، الرسالة، والموافقة على الخصوصية.
- توضيح ما إذا كان التواصل عبر الهاتف أو واتساب أسرع حسب اعتماد الشركة.
- لا تضمّن خريطة ثقيلة تلقائيًا؛ يمكن تحميل الخريطة عند طلب المستخدم أو استخدام رابط خارجي.

## 7. تجربة الجوال والأجهزة المختلفة

### 7.1 نهج التصميم

- ابدأ بعرض الهاتف 360–390px ثم اختبر الشاشات الأصغر والأكبر.
- استخدم CSS Grid وFlexbox وContainer Queries عند الحاجة بدل تثبيت عرض العناصر.
- اعتمد وحدات مرنة مثل `%` و`rem` و`clamp()`، وتجنب الارتفاعات الثابتة التي تقطع النص.
- استخدم الخصائص المنطقية مثل `margin-inline` و`padding-inline` لدعم RTL/LTR.
- يجب ألا ينتج عن تبديل اللغة انقلاب ترتيب غير مقصود أو اختفاء الأيقونات.

### 7.2 مقاسات الاختبار

اختبر فعليًا على المقاسات التالية على الأقل، وليس فقط عبر محاكاة واحدة:

| الفئة | عرض الاختبار التقريبي |
|---|---|
| هاتف صغير | 320px و 360px |
| هاتف شائع | 375px و 390px |
| هاتف كبير | 430px |
| جهاز لوحي عمودي | 768px |
| جهاز لوحي كبير | 834px و 1024px |
| كمبيوتر محمول | 1280px و 1366px |
| شاشة مكتبية | 1440px و 1600px |
| شاشة عريضة | 1920px |

اختبر الاتجاهين العمودي والأفقي للهاتف واللوحي، وكذلك تكبير المتصفح 200%.

### 7.3 قواعد الجوال

- قائمة تنقل منسدلة أو لوحة جانبية واضحة، تغلق بالضغط خارجها وبزر الإغلاق وبزر Escape.
- الأزرار والروابط سهلة اللمس؛ اجعل المساحة المستهدفة مريحة، واستهدف 44–48px للعناصر الرئيسية حيثما أمكن.
- لا تجعل زر واتساب أو زر عائم يحجب حقول النموذج أو المحتوى.
- لا تستخدم شريط تنقل سفليًا مزدحمًا لموقع شركة ما لم يثبت اختبار المستخدمين فائدته.
- الصور تُقص بذكاء باستخدام `object-fit` ومواضع تركيز مناسبة لكل مقاس.
- لا تقطع عناوين العربية أو تخفي آخر كلمة بسبب ارتفاع ثابت.
- حقول الإدخال تظهر لوحة مفاتيح مناسبة لنوع البيانات: هاتف، بريد، أرقام.
- تكون النماذج عمودية، بعرض كامل، مع زر متابعة واضح وثابت بصريًا دون حجب المحتوى.

### 7.4 قواعد الكمبيوتر

- عرض محتوى مركزي مناسب، لا يمتد النص على كامل شاشة 1920px.
- قوائم واضحة مع مساحات بيضاء متوازنة.
- تخطيط أعمدة عند وجود محتوى يستفيد منه فعلًا.
- لا تستخدم فراغات ضخمة تجعل الصفحة تبدو خالية.
- راعِ الشاشات 1366×768 حيث قد يكون الارتفاع محدودًا.

## 8. الحركة والمؤثرات والتجربة البصرية

- استخدم حركات قصيرة وهادئة لتأكيد الانتقال أو التفاعل، وليس لاستعراض التقنية.
- يمكن إضافة حركة دخول لطيفة للعناصر عند ظهورها، مع تعطيلها عند تفعيل `prefers-reduced-motion`.
- لا تجعل حركة الخلفية أو الفيديو تؤخر ظهور العنوان أو زر الطلب.
- تجنب Parallax الثقيل، والمؤثرات ثلاثية الأبعاد التي لا تضيف قيمة، والتحميل المسبق لملفات كبيرة.
- استخدم حالات hover وfocus وpressed وdisabled واضحة.
- لا تعتمد على اللون وحده لإظهار النجاح أو الخطأ؛ أضف نصًا أو رمزًا مناسبًا.
- الانتقالات بين الصفحات يجب ألا تمنع الرجوع أو تسبب وميضًا أو شاشة بيضاء.
- استخدم رسومًا توضيحية بسيطة لمسار الشحن بدل تكديس مؤثرات غير ضرورية.

## 9. إدارة المحتوى ولوحة التحكم بالتفصيل

### 9.1 الأدوار والصلاحيات

أنشئ نظام صلاحيات من البداية مع أقل قدر من الامتيازات:

| الدور | الصلاحيات المقترحة |
|---|---|
| Super Admin | إدارة جميع المستخدمين والإعدادات والصلاحيات وسجلات التدقيق |
| Admin | إدارة المحتوى والخدمات والطلبات وفق التفويض |
| Sales / Operations | عرض الطلبات المسندة أو المسموح بها، تحديث الحالة، وإضافة ملاحظات داخلية |
| Content Editor | تحرير الصفحات والخدمات والأسئلة والمقالات دون إدارة المستخدمين |
| Viewer | قراءة التقارير والسجلات المسموح بها دون تعديل |

- تحقق من الصلاحية في الخادم لكل إجراء، لا تكتفِ بإخفاء الزر في الواجهة.
- سجّل عمليات تغيير الحالة والحذف وتعديل أرقام الاتصال والإعدادات.
- لا تسمح بمشاركة حساب إدارة واحد بين الجميع.

### 9.2 لوحة المعلومات

بطاقات إحصائية مرتبطة ببيانات فعلية:
- طلبات جديدة.
- طلبات قيد المراجعة.
- طلبات تحتاج إلى متابعة.
- طلبات مكتملة أو مغلقة.
- رسائل تواصل غير مقروءة.
- آخر الأنشطة.

لا تظهر أرقامًا ثابتة أو بيانات تجريبية في الإنتاج. أضف حالات فارغة مفيدة عند عدم وجود بيانات.

### 9.3 دورة حياة طلب عرض السعر

حالات قابلة للتخصيص، مثل:

`NEW` جديد ← `REVIEWING` قيد المراجعة ← `NEED_INFO` بانتظار معلومات ← `QUOTED` تم إرسال العرض ← `ACCEPTED` موافق عليه ← `IN_PROGRESS` قيد التنفيذ ← `COMPLETED` مكتمل ← `CLOSED` مغلق / `CANCELLED` ملغي.

- لا تجعل كل الحالات إلزامية إذا كان سير عمل الشركة مختلفًا.
- عند تغيير الحالة، أضف سجلًا يتضمن المستخدم والتاريخ والحالة السابقة والجديدة.
- الملاحظات الداخلية لا تظهر للعميل.
- لا تعرض السعر للعميل من النظام إلا إذا تم إدخاله واعتماده وإرسال إشعار مناسب.
- وفر بحثًا برقم الطلب أو الاسم أو الهاتف، وفلاتر بالتاريخ والحالة والخدمة والمسؤول.
- صدّر البيانات بصلاحية مخصصة، مع تسجيل عملية التصدير.

### 9.4 إدارة الخدمات والصفحات

لكل خدمة أو صفحة:
- عنوان عربي وإنجليزي.
- slug فريد لكل لغة أو آلية ربط منظمة بين النسخ.
- ملخص ومحتوى كامل.
- صورة رئيسية وصور اختيارية.
- نص بديل لكل صورة.
- حالة: مسودة / منشور / مخفي.
- ترتيب ظهور.
- عنوان SEO ووصفه وبيانات المشاركة.
- روابط الخدمات أو الصفحات المرتبطة.

### 9.5 إدارة الوسائط

- مكتبة صور تعرض معاينة واسم الملف والأبعاد والحجم وتاريخ الرفع.
- تحويل الصور إلى WebP أو AVIF عند ملاءمة المتصفح، مع بديل مناسب.
- لا تجعل الصورة وحدها تحمل النص الذي يحتاجه المستخدم.
- لا تحذف ملفًا مستخدمًا في صفحة منشورة دون تنبيه أو معالجة المرجع.
- لا تسمح برفع ملفات تنفيذية أو أنواع غير لازمة.

## 10. البيانات وقاعدة البيانات

صمم نموذج البيانات بناءً على الحاجة الفعلية، مع حقول واضحة ومفاتيح وعلاقات وقيود وفهارس مناسبة. الجداول/الكيانات الأولية:

- `AdminUser`: مستخدمو لوحة الإدارة.
- `Role` و`Permission` أو بديل RBAC واضح.
- `QuoteRequest`: طلبات عروض الأسعار.
- `QuoteAttachment`: مرفقات الطلبات وبياناتها الوصفية.
- `ContactMessage`: رسائل التواصل.
- `Service`: الخدمات.
- `Page`: الصفحات العامة وأقسامها.
- `FAQCategory` و`FAQItem`: الأسئلة الشائعة.
- `Article` و`ArticleCategory`: المقالات والتصنيفات.
- `Destination` أو `CoverageArea`: المناطق المعتمدة.
- `CompanySetting`: بيانات الشركة ووسائل التواصل والإعدادات العامة.
- `MediaAsset`: ملفات الوسائط.
- `AuditLog`: سجل العمليات الإدارية.
- `NotificationLog`: سجل إشعارات البريد أو الرسائل.
- `Shipment` و`ShipmentEvent`: لا تُنشأ كبيانات تشغيلية إلا إذا كان هناك مصدر حقيقي لإدارة الشحنات أو تكامل تتبع.

### ضوابط قاعدة البيانات

- استخدم معرفات داخلية لا تكشف أعداد الطلبات أو تسلسلها للزوار.
- أنشئ رقم طلب مرجعيًا عشوائيًا/غير قابل للتخمين.
- أضف `createdAt` و`updatedAt` حيث يلزم، ومعلومات منشئ/معدل السجل للكيانات الحساسة.
- استخدم Soft Delete حيث يلزم للحفاظ على سجل الأعمال، مع سياسة حذف فعلية للبيانات التي يجب التخلص منها.
- خزّن أرقام الهاتف كنص مع رمز الدولة، ولا تعاملها كعدد حسابي.
- خزّن التواريخ في قاعدة البيانات بصيغة زمنية معيارية، واعرضها بالمنطقة الزمنية المناسبة.
- لا تخزن كلمات مرور أو رموز API في جداول نصية عادية.

## 11. الواجهات الخلفية والتكاملات

اعزل الخدمات الخارجية خلف واجهات Provider/Adapter حتى يمكن تغيير المزود لاحقًا دون إعادة كتابة الموقع.

### 11.1 البريد الإلكتروني

- إعداد مزود بريد معاملات موثوق أو SMTP معتمد.
- قوالب عربية وإنجليزية لرسالة وصول طلب جديد، وتأكيد الاستلام، ورسائل التواصل.
- إرسال نسخة للفريق إلى البريد الذي تعتمده الشركة.
- سجّل حالات الإرسال والفشل وإعادة المحاولة بطريقة آمنة.
- اضبط SPF وDKIM وDMARC على نطاق الشركة عند توفر صلاحية إدارة DNS.

### 11.2 واتساب

- في المرحلة الأولى، يمكن فتح محادثة عبر رابط WhatsApp Click to Chat إذا تم تأكيد الرقم.
- لا تدّعِ أن الموقع يرسل رسائل تلقائية من واتساب دون إعداد WhatsApp Business Platform أو مزود معتمد وموافقة الشركة.
- إذا فُعّل الإرسال الآلي لاحقًا، استخدم قوالب ورسائل معتمدة، واحفظ مفاتيح الربط في الخادم فقط.

### 11.3 التخزين والمرفقات

- استخدم تخزينًا خاصًا للمرفقات، مع روابط مؤقتة عند الحاجة.
- تحقّق من امتداد الملف ونوعه الحقيقي ومحتواه، ولا تعتمد على `Content-Type` المرسل من المتصفح وحده.
- ضع حدودًا للحجم والعدد والأنواع المسموحة.
- غيّر أسماء الملفات إلى أسماء مولدة من النظام.
- امنع تنفيذ الملفات أو عرضها inline إذا كان ذلك يسبب خطرًا.
- افحص الملفات بخدمة حماية مناسبة متى توفرت.
- لا تجعل مرفقات العملاء متاحة عبر روابط عامة دائمة.

### 11.4 نظام التتبع

أنشئ واجهة تكامل مستقلة مثل `TrackingProvider`:
- `lookup(trackingNumber)` يعيد بيانات موثوقة ومهيكلة.
- تعامل مع حالات: غير موجود، غير متاح مؤقتًا، تجاوز حد الاستعلام، خطأ من المزود.
- سجّل مصدر كل تحديث ووقت جلبه.
- لا تخمّن موعد الوصول ولا تغيّر حالة الشحنة محليًا لتبدو محدثة.
- إذا كان التتبع عبر نظام داخلي، يجب أن يكون تحديث الحالات من موظف مخوّل مع سجل تدقيق.

### 11.5 الخرائط

- استخدم رابط خرائط إلى الموقع بعد تأكيد العنوان والإحداثيات.
- لا تضع Map iframe ثقيلًا في أعلى الصفحة؛ اجعل تحميله عند الحاجة.
- أضف عنوانًا نصيًا دائمًا بجانب الخريطة حتى لا تكون الخريطة الوسيلة الوحيدة لمعرفة الموقع.

## 12. الأمان والخصوصية

طبّق أساسيات OWASP Top 10:2025 وأفضل الممارسات الأمنية الحديثة.

### 12.1 حسابات الإدارة

- كلمات المرور تخزن باستخدام خوارزمية قوية مخصصة لكلمات المرور مثل Argon2id أو ما يعادلها الموثوق.
- جلسات آمنة عبر Cookies تحمل `HttpOnly` و`Secure` في الإنتاج و`SameSite` مناسب.
- إضافة مصادقة متعددة العوامل لحسابات الإدارة، ويفضّل إلزام المسؤول الأعلى بها.
- تحديد محاولات تسجيل الدخول ومنع التخمين الآلي.
- استعادة كلمة المرور برمز محدود الصلاحية أحادي الاستخدام.
- إنهاء الجلسات عند تغيير كلمة المرور أو تعطيل المستخدم.
- لا تستخدم كلمة مرور افتراضية ثابتة في الإنتاج.

### 12.2 حماية التطبيق

- تحقق من صلاحيات القراءة والإنشاء والتعديل والحذف في الخادم.
- حماية من SQL Injection وXSS وCSRF وSSRF وOpen Redirect وفق أسلوب الإطار.
- تحقق من كل مدخل على الخادم، حتى لو تم التحقق منه في المتصفح.
- استخدم استعلامات parameterized عبر ORM.
- أضف Security Headers مناسبة، وسياسة CSP مدروسة.
- استخدم HTTPS فقط في الإنتاج، وأعد توجيه HTTP إلى HTTPS.
- فعّل Rate Limiting للنماذج وتسجيل الدخول وتتبع الشحنات.
- أضف حماية ضد الرسائل المزعجة مثل honeypot أو CAPTCHA عند الضرورة، دون إفساد سهولة الاستخدام.
- لا تكشف stack traces أو تفاصيل قاعدة البيانات للزوار.
- حدّث الاعتماديات دوريًا، وافحص الثغرات قبل النشر.

### 12.3 حماية بيانات العملاء

- اجمع البيانات الضرورية فقط.
- وضّح سبب جمع رقم الهاتف والبريد والمرفقات.
- لا تجعل بيانات الطلبات أو المرفقات عامة.
- حدد من يستطيع مشاهدة بيانات العميل.
- اعتمد مدة احتفاظ بالبيانات وسياسة حذف/إخفاء مناسبة للشركة والمتطلبات القانونية ذات الصلة.
- لا تضع بيانات شخصية داخل روابط عامة أو سجلات تحليلات.
- وثّق طريقة التعامل مع طلبات التصحيح أو الحذف عند انطباقها.

## 13. SEO والظهور في محركات البحث

### 13.1 SEO تقني

- HTML دلالي وعناوين H1/H2/H3 مرتبة.
- عنوان ووصف Meta فريدان لكل صفحة ولكل لغة.
- روابط قصيرة مفهومة، دون معرّفات أو معاملات غير لازمة.
- `canonical` صحيح لكل صفحة.
- `hreflang` للنسخ العربية والإنجليزية المتقابلة، بما فيها `x-default` عند الحاجة.
- `sitemap.xml` ديناميكي يضم الصفحات المنشورة فقط.
- `robots.txt` مضبوط دون حجب ملفات CSS/JS الضرورية.
- Open Graph وTwitter/X Cards بصور وأوصاف مناسبة.
- Breadcrumbs في الصفحات الداخلية.
- صفحات 404 و301 صحيحة، وتجنب سلاسل التحويل.
- لا تفهرس صفحات الإدارة أو نتائج النماذج أو صفحات النتائج الخاصة أو البحث الداخلي.

### 13.2 البيانات المنظمة Structured Data

أضف JSON-LD فقط عندما تطابق البيانات الظاهرة والحقيقية:
- `Organization` على الصفحة الرئيسية أو من نحن.
- `LocalBusiness` أو النوع الأكثر تخصّصًا فقط عند تطابق طبيعة النشاط وتوفر بيانات المكتب الدقيقة.
- `Service` لصفحات الخدمات عند ملاءمة المحتوى.
- `Article` للمقالات.
- `BreadcrumbList` لمسارات التنقل.

لا تضف تقييمات نجوم أو أسعارًا أو بيانات فروع أو ساعات عمل غير حقيقية. اختبر البيانات المنظمة بأدوات Google قبل الإطلاق.

### 13.3 المحتوى والكلمات المفتاحية

استهدف عبارات بحث فعلية بعد بحث الكلمات المفتاحية، ومنها كبداية فقط:
- شركة شحن في اليمن.
- خدمات الاستيراد إلى اليمن.
- الشحن إلى اليمن.
- التخليص الجمركي في اليمن.
- خدمات الشحن البحري إلى اليمن (إذا كانت الخدمة مؤكدة).
- الشحن الجوي إلى اليمن (إذا كانت الخدمة مؤكدة).
- Sama Capital shipping and customs clearance.

لا تحشو الكلمات المفتاحية. اكتب محتوى مفيدًا يجيب عن احتياج العميل، وميّز صفحات الخدمات حتى لا تكون نسخًا مكررة.

### 13.4 اللغات

- لكل صفحة عربية نسخة إنجليزية حقيقية مترجمة باحتراف، لا ترجمة آلية حرفية غير مراجعة.
- لا تخلط العربية والإنجليزية في ترتيب واحد يربك اتجاه القراءة.
- استخدم `lang="ar" dir="rtl"` للعربية و`lang="en" dir="ltr"` للإنجليزية.
- عند تغيير اللغة، انقل الزائر إلى الصفحة المقابلة إن كانت موجودة؛ وإلا انقله إلى القسم المناسب أو الرئيسية مع توضيح ذلك.
- احفظ اختيار اللغة في Cookie أو إعداد متزن، ولا تفرض تحويلًا قسريًا على كل زيارة.

## 14. الأداء والسرعة والاستقرار

### 14.1 أهداف Core Web Vitals

استهدف في بيانات المستخدمين الفعلية (عند توفرها) القيم الجيدة التالية:
- LCP: لا يزيد عن 2.5 ثانية.
- INP: أقل من 200ms.
- CLS: أقل من 0.1.

هذه أهداف قياس وليست ضمانًا لكل شبكة أو جهاز. اختبر عبر Lighthouse وPageSpeed Insights وبيانات Search Console عند توفرها.

### 14.2 تحسين الصور والوسائط

- الشعار بصيغة SVG نظيفة أو PNG شفاف عالي الجودة عند عدم توفر SVG.
- صور المحتوى WebP/AVIF مع بدائل مناسبة.
- أنشئ أحجامًا متعددة للصور حسب العرض الفعلي.
- أضف أبعاد الصور أو نسبة أبعاد ثابتة لتجنب قفز التخطيط.
- لا تستخدم Lazy Loading لصورة Hero الرئيسية إذا كانت عنصر LCP؛ استخدم أولوية تحميل مناسبة.
- استخدم Lazy Loading للصور أسفل الجزء الظاهر.
- اضغط الصور مع الحفاظ على جودة واضحة.
- لا تضع فيديو خلفية كبيرًا في الهاتف افتراضيًا.

### 14.3 تحسين الكود

- تقليل JavaScript المرسل إلى المتصفح.
- تحميل المكونات التفاعلية عند الحاجة.
- عدم استخدام مكتبات ضخمة لتأثير بسيط.
- تجنب تكرار الطلبات إلى قاعدة البيانات.
- استخدام caching وrevalidation وفق طبيعة كل نوع بيانات؛ بيانات الطلبات لا تُخزّن في Cache عام.
- تحليل bundle في كل مرحلة إنتاجية.
- استخدم Skeleton مناسبًا عند تحميل البيانات بدل شاشة بيضاء.
- تعامل مع الشبكات البطيئة وفشل الخدمات الخارجية برسائل واضحة.

### 14.4 مراقبة الأخطاء

- أداة تسجيل أخطاء للخادم والواجهة بعد اعتمادها.
- إخفاء البيانات الشخصية من تقارير الأخطاء.
- مراقبة uptime ونقاط الصحة.
- تنبيه المسؤول عند فشل إرسال إشعار أو تعطل قاعدة البيانات أو خدمة التتبع.
- سجلات منظمة مع request ID لتسهيل تتبع المشكلة.

## 15. إمكانية الوصول (Accessibility)

استهدف مستوى **WCAG 2.2 AA** قدر الإمكان.

- تشغيل كامل بلوحة المفاتيح.
- مؤشر Focus واضح لا يُخفى خلف الرأس الثابت.
- ترتيب Tab منطقي من اليمين إلى اليسار بصريًا، مع ترتيب DOM صحيح.
- تسميات حقيقية لكل الحقول، لا تعتمد على Placeholder وحده.
- ربط رسائل الخطأ بالحقول عبر `aria-describedby`.
- تباين نصوص وأزرار واضح.
- نص بديل وصفي للصور المهمة، وalt فارغ للصور الزخرفية.
- عناوين وأدوار HTML دلالية.
- إدارة Focus داخل Dialog والقوائم الجانبية.
- إعلان رسائل النجاح والخطأ لقارئات الشاشة.
- احترام `prefers-reduced-motion`.
- لا تستخدم لونًا وحده لتوضيح الحالة.
- لا تمنع تكبير النص أو الصفحة.
- راعِ الحد الأدنى للمساحة المستهدفة للعناصر التفاعلية.

## 16. الاختبارات المطلوبة قبل التسليم

### 16.1 اختبارات الوظائف

- كل عنصر في قائمة التنقل يفتح الصفحة الصحيحة.
- جميع الروابط الداخلية والخارجية تعمل.

- Chrome على Android.
- Safari على iPhone إن توفر جهاز اختبار.

- اختبار لوحة المفاتيح يدويًا.

- مراجعة تباين النصوص.
- اختبار قارئ شاشة لعناصر النموذج الأساسية عند توفر بيئة الاختبار.

### 16.4 اختبارات الأمان

- الوصول المباشر إلى صفحات الإدارة دون تسجيل دخول.
- محاولة تنفيذ عمليات إدارية بحساب لا يملك الصلاحية.
- التحقق من Rate Limiting.
- اختبار إدخالات غير صالحة ونصوص HTML غير موثوقة.
- رفع ملف غير مسموح به أو أكبر من الحد.
- التأكد من أن المرفقات خاصة.
- مراجعة عدم وجود أسرار في ملفات JavaScript أو المستودع.
- فحص الاعتماديات والثغرات.

### 16.5 اختبارات المحتوى

- صحة الاسم العربي والإنجليزي والشعار.

## 22. المعلومات والمواد المطلوب استلامها من الشركة

على المطور إعداد قائمة متابعة بهذه البيانات وعدم افتراضها:

1. ملف الشعار الأصلي Vector بصيغة SVG أو PDF أو AI، ونسخة PNG شفافة عالية الجودة.
2. الاسم القانوني المسجل للشركة إن كان مختلفًا عن الاسم التجاري.
3. وصف رسمي مختصر للشركة بالعربية والإنجليزية.
4. قائمة الخدمات التي تقدمها الشركة فعليًا، مع تفاصيل وحدود كل خدمة.
5. هل الشحن بحري وجوي وبري كلها متاحة؟ وما الذي يتم عبر الشركة أو عبر شركاء؟
6. الدول والمدن التي يمكن الشحن منها وإليها، والمدن التي تتم تغطيتها داخل اليمن.
7. أرقام الهاتف النهائية، وما إذا كان كل رقم مكالمات أو واتساب أو قناة خاصة بفريق معين.
8. البريد الإلكتروني الرسمي وبريد استقبال طلبات الأسعار.
9. العنوان الدقيق، ساعات العمل، والمنطقة الزمنية.
10. روابط حسابات التواصل الاجتماعي الرسمية.
11. الصور الأصلية للمكتب والمستودعات والعمليات والفريق، مع أذونات استخدامها.
12. سياسة الشركة في البضائع الممنوعة أو المقيدة، والمستندات المطلوبة.
13. آلية طلب عرض السعر: من يستلمه؟ من يراجعه؟ من يرسل السعر؟
14. هل يوجد نظام داخلي أو API حقيقي لتتبع الشحنات؟ ومن يملك صلاحية الربط به؟
15. هل تريد الشركة إدارة الطلبات بالكامل من لوحة الموقع أم يكفي إرسالها إلى البريد/واتساب؟
16. من المسؤول عن اعتماد المحتوى العربي والإنجليزي والسياسات القانونية؟
17. اسم النطاق والاستضافة وصلاحيات DNS وبيئة البريد.
18. سياسة مدة الاحتفاظ ببيانات العملاء والمرفقات.

## 23. تعليمات تجربة التصميم المطلوبة

استلهم من الصور المرفقة ألوان الأزرق والبرتقالي ورموز الطائرة والسفينة والحاويات، لكن لا تنسخ الملصقات الإعلانية كما هي داخل الموقع. المطلوب نظام تصميم احترافي جديد يناسب موقع شركة:

- Hero بصري قوي لكن بسيط، مع صورة حقيقية عالية الجودة ومساحة نص كافية.
- بطاقات خدمات أنيقة ومتناسقة.
- رسومات مسار شحن بسيطة عند الحاجة.
- استخدام البرتقالي لتوجيه الانتباه لا لتلوين كل عنصر.
- خلفيات بيضاء وفاتحة مع أقسام زرقاء داكنة مدروسة.
- صور لا تبدو كقصاصات مركبة أو صور منخفضة الدقة.
- تجنب الصور النمطية المكررة التي لا تمثل الخدمات الحقيقية.
- لا تضع الشعار صغيرًا جدًا أو مضغوطًا أو مشوهًا.
- حافظ على المحاذاة والمسافات واتساق أحجام العناوين.
- أعطِ الأولوية للوضوح وسهولة الإجراء على كثرة المؤثرات.

## 24. ما لا يجب فعله

- لا تبنِ الموقع كقالب جاهز عام وتكتفِ بتغيير الشعار والألوان.
- لا تجعل الصفحة الرئيسية طويلة جدًا بلا تقسيم بصري أو هدف واضح.
- لا تستخدم صورًا أو أيقونات غير متناسقة.
- لا تكتب معلومات قانونية أو جمركية حاسمة دون مراجعة الشركة.
- لا تضع رسومًا أو أسعارًا أو مدد شحن غير معتمدة.
- لا تضف عدادات أرقام متحركة بقيم وهمية.
- لا تضف تقييمات عملاء وهمية أو أسماء شركات غير مصرح بعرضها.
- لا تجعل اختيار اللغة يترك المستخدم في صفحة فارغة.
- لا تضع رابط تتبع وهميًا.
- لا تسمح بتسريب معلومات طلب عميل لزائر آخر.
- لا تخزن ملفات العملاء داخل مجلد عام يمكن تخمين روابطه.
- لا تؤجل اختبار الجوال أو إمكانية الوصول إلى نهاية المشروع.
- لا تسلّم المشروع دون تعليمات تشغيل أو دون ملف البيئة النموذجي أو دون ترحيلات قاعدة البيانات.

## 25. المخرجات التي يجب أن يستلمها صاحب الشركة

1. رابط الموقع المنشور بعد موافقة الشركة.
2. رابط لوحة الإدارة وحساب مسؤول أول يتم إنشاؤه وتسليمه بطريقة آمنة.
3. المستودع البرمجي كاملًا مع سجل واضح للتغييرات.
4. ملف `README.md` تقني للتثبيت والتشغيل.
5. ملف `.env.example` دون أي أسرار.
6. قاعدة البيانات ومخططها وترحيلاتها.
7. ملفات التصميم أو نظام المكونات المعتمد، بحسب أداة التصميم المستخدمة.
8. ملفات الشعار والصور بعد تجهيزها وتحسينها.
9. دليل استخدام لوحة الإدارة.
10. دليل النشر والتحديث والرجوع إلى إصدار سابق.
11. دليل النسخ الاحتياطي والاستعادة.
12. نتائج الاختبارات وقائمة المتصفحات والأجهزة التي تم اختبارها.
13. قائمة بالخدمات الخارجية التي تم ربطها ومالك كل حساب ومكان إعداد مفاتيحه — دون كشف المفاتيح داخل المستند.
14. قائمة بأي ميزة لم تُفعّل بعد، مع سبب واضح ومتطلبات تفعيلها.

## 26. الخلاصة التنفيذية للمطور

أنشئ موقعًا مؤسسيًا حديثًا لشركة **سما كابيتال SAMA CAPITAL** متخصصًا في تقديم خدمات الاستيراد والشحن والتخليص الجمركي التي تعتمدها الشركة. يجب أن يجمع بين هوية بصرية زرقاء وبرتقالية مستوحاة من الشعار، وتجربة عربية RTL وإنجليزية LTR، وتصميم متجاوب شامل، وصفحات تعريفية وخدمية متكاملة، ونموذج طلب عرض سعر متعدد الخطوات، وصفحة تواصل، ولوحة إدارة فعلية لمتابعة الطلبات وتحديث المحتوى.

الأولوية ليست كثرة المؤثرات؛ الأولوية أن يفهم الزائر الخدمة بسرعة، ويثق بالمعلومات، ويستطيع التواصل أو إرسال طلبه بسهولة من أي جهاز. اجعل الموقع سريعًا، آمنًا، قابلًا للتطوير، سهل الإدارة، ومهيأً لمحركات البحث. لا تعرض أي خدمة أو رقم أو ادعاء أو تتبع أو سعر إلا بعد التحقق منه واعتماده. لا تسلّم صفحات شكلية أو وظائف غير مكتملة. **اعتبر المشروع منتهيًا فقط عندما تعمل رحلة المستخدم كاملة من أول زيارة إلى وصول الطلب إلى لوحة الإدارة وإمكانية متابعته من الموظف المخوّل.**
